## Heuristic Navigation in Westeros

# 1. زیرساخت مشترک در `infrastructure.py`

برای جلوگیری از تکرار کد در فایل‌های مختلف search، یک کلاس کمکی به نام `ManOfTheNightsWatch` در فایل `infrastructure.py` تعریف شده است. این کلاس نقش یک adapter بین الگوریتم‌های search و محیط بازی را دارد.

الگوریتم‌هایی مثل `bfs.py`، `ucs.py`، `dls.py` و `a_star.py` نباید مستقیماً درگیر جزئیات زیاد `GameState` شوند. به همین دلیل، بخش‌هایی مثل ساختن کلید یکتا برای state، گرفتن successorها، و فیلتر کردن برخوردهای خطرناک در این کلاس انجام می‌شود.

## 1.1 متد `state_key`

مهم‌ترین وظیفه `state_key` این است که از هر `GameState` یک نمایش hashable بسازد. این کلید برای تشخیص state های تکراری در `visited set` یا `visited dictionary` استفاده میشود.

در این پروژه، کلید state شامل موارد زیر است:

- موقعیت فعلی agent؛
- مجموعه targetهای باقی‌مانده؛
- وضعیت چرخه حرکت دشمن؛
- داشتن یا نداشتن weapon؛
- زنده بودن یا نبودن Night King.

این اطلاعات برای تصمیم‌گیری الگوریتم کافی هستند. مثلاً اگر Arya در یک خانه مشخص باشد، اما targetهای باقی‌مانده متفاوت باشند، این دو حالت نباید یکی در نظر گرفته شوند. همچنین اگر weapon گرفته شده باشد یا Night King کشته شده باشد، رفتار آینده محیط تغییر می‌کند، پس این موارد هم باید در state key لحاظ شوند.

## 1.2 متد `next_states`

متد `next_states` مسئول تولید حالت‌های بعدی است. این متد از تابع آماده محیط یعنی `get_successors()` استفاده می‌کند و خروجی آن را به شکل قابل استفاده برای search برمی‌گرداند.

هر successor شامل سه بخش است:

- action انجام‌شده؛
- cost آن حرکت؛
- state جدید بعد از انجام action.

در صورت فعال بودن `avoid_collision`، این متد successorهایی را که باعث collision خطرناک می‌شوند حذف می‌کند. این کار مخصوصا برای الگوریتم‌های uninformed مثل **BFS**، **UCS** و **DLS** مفید است، چون این الگوریتم‌ها خودشان درک خاصی از خطر Night King ندارند.

برای **A\***، برخورد با دشمن کمی دقیق‌تر مدیریت شده است، چون در حالت bonus اگر Arya weapon داشته باشد، برخورد با Night King دیگر شکست نیست و حتی می‌تواند باعث کشتن دشمن شود.

# 2. الگوریتم BFS

## 2.1 هدف BFS

الگوریتم **BFS** یا **Breadth-First Search** یک الگوریتم uninformed است. این الگوریتم stateها را بر اساس عمق بررسی می‌کند؛ یعنی ابتدا تمام مسیرهای با طول ۱، سپس طول ۲، سپس طول ۳ و همین‌طور ادامه می‌دهد.

در این پروژه، BFS کوتاه‌ترین مسیر را از نظر تعداد action پیدا می‌کند، نه از نظر cost واقعی مسیر.

بنابراین اگر یک مسیر کوتاه از روی خانه‌های پرهزینه ice عبور کند، BFS ممکن است همان مسیر را انتخاب کند، حتی اگر مسیر دیگری با تعداد حرکت بیشتر ولی cost کمتر وجود داشته باشد.

## 2.2 ساختار داده BFS

در پیاده‌سازی BFS از `deque` استفاده شده است. دلیل استفاده از `deque` این است که BFS به یک queue از نوع FIFO نیاز دارد.

هر عضو queue شامل این اطلاعات است:

`current_state, path`

که در آن `path` لیست actionهایی است که از state اولیه تا state فعلی انجام شده‌اند.

همچنین یک `visited set` نگهداری می‌شود تا stateهای تکراری دوباره expand نشوند.

## 2.3 روند اجرای BFS

روند کلی BFS در پروژه به این شکل است:

1. state اولیه وارد queue می‌شود.
2. state اولیه در `visited` قرار می‌گیرد
3. در هر مرحله، قدیمیترین state از queue خارج میشود
4. اگر state فعلی goal باشد، path برگردانده می‌شود
5. اگر goal نباشد، successorهای مجاز تولید می‌شوند
6. هر successor که قبلاً دیده نشده باشد وارد queue میشود
7. اگر هیچ راه‌حلی پیدا نشود، path خالی برگردانده می‌شود

## 2.4 تحلیل BFS

مزیت BFS این است که ساده، کامل و قابل اعتماد است. اگر فضای state محدود باشد و راه‌حل وجود داشته باشد، BFS آن را پیدا می‌کند.

اما مشکل اصلی BFS این است که cost را در نظر نمی‌گیرد. در این پروژه که زمین‌های مختلف cost متفاوت دارند، این موضوع باعث می‌شود BFS همیشه بهترین مسیر از نظر score یا cost نهایی نباشد.

به همین دلیل، BFS بیشتر به عنوان یک baseline برای مقایسه با الگوریتم‌های پیشرفته‌تر استفاده شده است.

# 3. الگوریتم UCS

## 3.1 هدف UCS

الگوریتم **UCS** یا **Uniform Cost Search** نسخه cost-aware از search است. برخلاف BFS که فقط تعداد stepها را در نظر می‌گیرد، UCS همیشه مسیری را expand می‌کند که تا آن لحظه کمترین cost را داشته باشد.
در این پروژه، UCS اهمیت زیادی دارد، چون حرکت روی خانه‌های معمولی، برفی، یخی، یا برخورد با دشمن costهای متفاوتی دارند.

## 3.2 ساختار داده UCS

در UCS از `priority queue` استفاده شده است که با `heapq` پیاده‌سازی شده است.

هر عضو priority queue شامل این موارد است:
`current_cost, counter, current_state, path`

در اینجا `current_cost` همان `g(n)` است، یعنی هزینه واقعی مسیر از initial state تا state فعلی.

متغیر `counter` برای جلوگیری از خطای مقایسه بین stateها استفاده می‌شود. چون اگر دو state priority یکسان داشته باشند، Python ممکن است بخواهد خود stateها را با هم مقایسه کند و این باعث error می‌شود.

## 3.3 visited در UCS

در UCS، برخلاف BFS، فقط دانستن اینکه یک state قبلاً دیده شده کافی نیست. ممکن است یک state قبلاً با cost بالا دیده شده باشد، اما بعداً با cost کمتر دوباره پیدا شود.
برای همین در UCS از dictionary استفاده شده است:
`visited[state_key] = best_cost`

اگر الگوریتم به همان state با cost کمتر برسد، مقدار قبلی به‌روزرسانی می‌شود و state دوباره وارد priority queue می‌شود.

## 3.4 روند اجرای UCS

روند UCS به این شکل است:

1. state اولیه با cost صفر وارد priority queue می‌شود.
2. state با کمترین cost از صف خارج می‌شود.
3. اگر state فعلی goal باشد، path برگردانده می‌شود.
4. successorهای مجاز تولید می‌شوند.
5. برای هر successor، cost جدید محاسبه می‌شود.
6. اگر این cost از cost قبلی بهتر باشد، successor در queue قرار می‌گیرد.

## 3.5 تحلیل UCS

UCS در صورتی که costها مثبت باشند، کامل و optimal است. یعنی اگر اجازه داشته باشد کامل اجرا شود، کم‌هزینه‌ترین مسیر را پیدا می‌کند.
اما نقطه ضعف UCS این است که heuristic ندارد. یعنی نمی‌داند targetها کجا هستند و فقط بر اساس cost طی‌شده جلو می‌رود. در نقشه‌های بزرگ، این باعث expand شدن تعداد زیادی state می‌شود.
بنابراین UCS برای مسیرهای cost-sensitive مناسب است، اما نسبت به A\* کندتر است.

# 4. الگوریتم DLS / IDS

## 4.1 هدف DLS

الگوریتم **DLS** یا **Depth-Limited Search** یک search عمقی با محدودیت depth است. در این پروژه، پیاده‌سازی به شکل iterative انجام شده است؛ یعنی depth limit از مقدار کم شروع می‌شود و به‌تدریج افزایش پیدا می‌کند.

این روش شبیه **IDS** یا **Iterative Deepening Search** است.

## 4.2 روند اجرا

تابع اصلی، برای depth limitهای مختلف search را اجرا می‌کند. در هر depth، تابع recursive زیر استفاده می‌شود:

`depth_limited_search(state, depth, path, visited)`

این تابع بررسی می‌کند:

1. آیا state فعلی goal است یا نه؛

2. آیا depth به صفر رسیده یا نه؛

3. آیا این state قبلاً با depth بهتر یا برابر دیده شده یا نه؛

4. سپس successorها را به صورت recursive بررسی می‌کند.

## 4.3 visited در DLS

برای جلوگیری از تکرارهای غیرضروری، در DLS از dictionary استفاده شده است:

`visited[key] = depth`

اگر یک state قبلاً با depth باقی‌مانده بیشتر یا مساوی دیده شده باشد، بررسی دوباره آن فایده‌ای ندارد. این کار باعث می‌شود تعداد expandها کمتر شود.

## 4.4 تحلیل DLS

مزیت DLS این است که memory کمتری نسبت به BFS مصرف می‌کند، چون مسیرها را به صورت عمقی بررسی می‌کند.

اما مشکل آن این است که اگر depth limit مناسب نباشد، ممکن است راه‌حل را پیدا نکند. IDS این مشکل را تا حدی حل می‌کند، چون depth limit را به‌تدریج افزایش می‌دهد.

با این حال، IDS ممکن است بعضی stateها را چندین بار در depthهای مختلف بررسی کند. بنابراین در نقشه‌های بزرگ می‌تواند کند باشد.

# 5. الگوریتم A\*

## 5.1 هدف A\*

الگوریتم **A\*** مهم‌ترین الگوریتم پروژه است، چون از heuristic برای کاهش تعداد expanded nodes استفاده می‌کند.

A\* برخلاف UCS فقط به cost طی‌شده توجه نمی‌کند، بلکه یک تخمین از cost باقی‌مانده تا goal هم در نظر می‌گیرد.

فرمول کلی آن به این شکل است:

`f(n) = g(n) + h(n)`

در پیاده‌سازی ما، از وزن heuristic هم استفاده شده است:

`f(n) = g(n) + weight * h(n)`

مقدار `HEURISTIC_WEIGHT` برابر `1.15` در نظر گرفته شده است. این باعث می‌شود الگوریتم کمی تهاجمی‌تر به سمت targetها حرکت کند و تعداد expanded nodes کمتر شود. البته چون heuristic وزن‌دار شده، این نسخه از A\* دیگر تضمین strict optimality ندارد، اما برای هدف پروژه که کاهش expanded nodes است، عملکرد بهتری می‌دهد.

---

## 5.2 ساختار داده A\*

A\* هم مثل UCS از `priority queue` با `heapq` استفاده می‌کند.

هر عضو queue شامل این اطلاعات است:

`f, h, counter, g, state, path`

در اینجا:

- `g` هزینه واقعی مسیر تا state فعلی است؛

- `h` تخمین heuristic از هزینه باقی‌مانده است؛

- `f` مجموع این دو مقدار با وزن heuristic است؛

- `path` مسیر طی‌شده تا state فعلی است.

الگوریتم همیشه stateای را expand می‌کند که کمترین مقدار `f` را داشته باشد.

---

# 6. Heuristic در A\*

Heuristic پیاده‌سازی‌شده فقط یک فاصله ساده نیست. هدف آن این است که با محیط تعامل داشته باشد و وضعیت واقعی map را بهتر درک کند.

برای همین چند بخش مختلف در heuristic استفاده شده است.

## 6.1 Manhattan Distance

اولین بخش heuristic، استفاده از **Manhattan Distance** است. چون حرکت agent فقط در چهار جهت اصلی انجام می‌شود، Manhattan Distance انتخاب مناسبی برای تخمین فاصله است.

این فاصله با minimum step cost ضرب می‌شود تا به cost تقریبی تبدیل شود.

---

## 6.2 نزدیک‌ترین target

Heuristic ابتدا فاصله agent تا نزدیک‌ترین target باقی‌مانده را محاسبه می‌کند. این باعث می‌شود A\* بی‌هدف در map پخش نشود و به سمت نزدیک‌ترین هدف مفید حرکت کند.

اما فقط نزدیک‌ترین target کافی نیست، چون agent باید همه targetها را جمع کند، نه فقط یکی را.

---

## 6.3 MST برای targetهای باقی‌مانده

برای اینکه heuristic دید کلی‌تری نسبت به تمام targetها داشته باشد، از ایده **MST** یا **Minimum Spanning Tree** استفاده شده است.

MST یک تخمین از حداقل هزینه لازم برای متصل کردن تمام targetهای باقی‌مانده می‌دهد. این روش کمک می‌کند A\* بفهمد بعد از رسیدن به یک target، هنوز چه مقدار کار باقی مانده است.

همچنین برای افزایش سرعت، مقدار MST برای مجموعه targetهای تکراری در `mst_cache` ذخیره می‌شود. این کار باعث می‌شود heuristic بارها و بارها برای یک مجموعه مشابه محاسبه نشود.

---

## 6.4 Nearest-Neighbour Chain

در کنار MST، یک تخمین greedy هم استفاده شده است. این تخمین از موقعیت فعلی شروع می‌کند، نزدیک‌ترین target را انتخاب می‌کند، سپس از آن target به نزدیک‌ترین target بعدی می‌رود و همین روند را ادامه می‌دهد.

این روش با نام `nearest_neighbour_chain` پیاده‌سازی شده است.

MST یک تخمین کلی و global می‌دهد، اما nearest-neighbour chain شبیه‌تر به یک مسیر واقعی است. ترکیب این دو باعث شده heuristic قوی‌تر عمل کند.

---

## 6.5 Target Progress Bonus

در heuristic، تعداد targetهای باقی‌مانده هم مهم است. stateای که targetهای کمتری باقی گذاشته باشد معمولاً بهتر است.

برای همین، heuristic نسبت به تعداد targetهای باقی‌مانده حساس شده است. این کار باعث می‌شود A\* متوجه شود که جمع کردن target خودش یک پیشرفت مهم است، نه فقط جابه‌جا شدن روی map.

---

## 6.6 در نظر گرفتن Ice

چون حرکت روی ice cost زیادی دارد، heuristic نسبت به targetهایی که روی خانه‌های پرهزینه قرار دارند حساس شده است.

این بخش کمک می‌کند A\* مسیرهایی را که ظاهراً از نظر فاصله کوتاه هستند ولی از نظر cost گران تمام می‌شوند، کمتر انتخاب کند.

---

## 6.7 در نظر گرفتن Night King

Heuristic نسبت به فاصله Arya از Night King هم حساس است. اگر Arya هنوز weapon نداشته باشد، نزدیک شدن به Night King خطرناک است.

برای همین اگر فاصله agent از enemy کم باشد، heuristic penalty اضافه می‌کند. هرچه فاصله کمتر باشد، penalty بیشتر می‌شود.

این کار باعث می‌شود A\* نسبت به enemy کور نباشد و مسیرهای خطرناک را کمتر انتخاب کند.

---

# 7. بخش Bonus: Weapon و کشتن Night King

در بخش bonus، بعضی mapها دارای weapon هستند. اگر Arya به خانه weapon برسد، وضعیت `has_weapon` فعال می‌شود. بعد از آن، برخورد با Night King دیگر شکست محسوب نمی‌شود.

اگر Arya با weapon به خانه Night King برسد، دشمن حذف می‌شود و وضعیت `is_enemy_alive` برابر false می‌شود.

بعد از کشته شدن Night King:

- enemy دیگر تهدیدی برای agent نیست؛

- collision penalty حذف می‌شود؛

- مسیرهای بعدی آزادتر و امن‌تر می‌شوند.

نکته مهم این است که الگوریتم نباید همیشه weapon را انتخاب کند. طبق صورت پروژه، agent باید هوشمندانه تصمیم بگیرد که آیا رفتن به سمت weapon و کشتن Night King به‌صرفه است یا نه.

در پیاده‌سازی A\*، heuristic هزینه تقریبی رفتن به سمت weapon و سپس enemy را با مسیر مستقیم مقایسه می‌کند. اگر گرفتن weapon و حذف enemy از نظر cost و reward منطقی باشد، مسیر weapon جذاب‌تر می‌شود. در غیر این صورت، agent صرفاً به خاطر وجود weapon مسیر خود را خراب نمی‌کند.
